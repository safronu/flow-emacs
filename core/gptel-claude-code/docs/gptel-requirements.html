gptel — Requirements Specification

Product: an LLM client for Emacs (“gptel”), supporting many providers, usable from any buffer. Audience: experienced Emacs Lisp developers who will implement the product from scratch. This document defines what to build; the companion gptel-architecture.md defines how. Baseline studied: gptel v0.9.9.5 (Emacs ≥ 27.1, Transient ≥ 0.7.8).

1. Product vision and design principles

The product is a Large Language Model chat client that works “in the spirit of Emacs: available at any time and uniformly in any buffer.” These principles are normative — they resolve design disputes:

  • P1 — Free-form interaction. Unlike clients that prescribe an interaction format (a comint shell, org-babel blocks), the user queries the model using any text in any buffer and redirects the response anywhere. A dedicated chat buffer exists but is only a convenience, never a requirement.
  • P2 — The buffer is the conversation. Conversation state (who said what) is carried by the buffer text itself plus invisible metadata (text properties), never by required syntactic markers. Users may freely edit both their prompts and the LLM’s past responses; the edited text is what gets sent.
  • P3 — Minimally annoying. The client never moves the user’s cursor, never steals focus, and never blocks Emacs. Auto-scroll and cursor-follow behaviors are opt-in.
  • P4 — Uniform across providers. One user-facing surface over 25+ LLM providers; provider differences are absorbed by a backend abstraction.
  • P5 — Transparent and programmable. The user can inspect and edit the exact request payload before sending, view raw logs, and build custom workflows on a public request API.
  • P6 — No hard external dependencies. Works with built-in Emacs facilities alone; uses curl opportunistically for streaming and robustness.

2. Glossary

Term Meaning
Backend A registered configuration for one provider endpoint (name, host, auth, models, wire dialect).
Model A provider model identifier plus metadata (capabilities, context window, costs, MIME types).
Chat buffer A buffer with the client’s minor mode enabled; gets prefixes, persistence, header-line UI.
Directive / system prompt The system message; may be a string, a function, or a string list (system message + canned conversation template).
Context Additional material (regions/buffers/files) attached to every request, distinct from the conversation text.
Tool A user-defined elisp function with a JSON-schema arg description that the LLM can call.
Preset A named bundle of option values applied together.
Scope Where an option change applies: globally, buffer-locally, or for the next request only (“oneshot”).
Dry-run Building a request fully without sending it, for inspection/editing/resumption.
Reasoning “Thinking” content some models emit before their answer.

3. Functional requirements

Requirement IDs are stable; the architecture document and test cases reference them.

3.1 Sending queries (FR-SEND)

  • FR-SEND-1 A single command (gptel-send) usable in any buffer sends the buffer text from the beginning up to point — extended to the end of the word at point — as the prompt. If a region is active, only the region is sent.
  • FR-SEND-2 The response is inserted asynchronously below the send position; Emacs remains fully usable during the request. Typing below the response and sending again continues the conversation (multi-turn).
  • FR-SEND-3 Past LLM responses within the sent text are recognized (see FR-TRACK) and encoded as assistant turns; everything else is user turns; the whole buffer parse yields a faithful multi-turn conversation including tool-call turns.
  • FR-SEND-4 Multiple requests may be in flight simultaneously, in the same or different buffers, without interference.
  • FR-SEND-5 An abort command stops the active request in the current buffer; partial output stays; the state is reported. Callbacks observe a distinct abort signal.
  • FR-SEND-6 A configurable limit on the number of prior conversation turns included with each request (N most recent user/assistant pairs; nil = all).
  • FR-SEND-7 On failure (HTTP error, connection error, malformed response), a human-readable status is surfaced (header line/echo area) including the HTTP status and provider error message; no partial garbage is inserted.
  • FR-SEND-8 Empty responses are reported as such (" Empty response") without inserting separators.

3.2 Response tracking and demarcation (FR-TRACK)

  • FR-TRACK-1 LLM responses are watermarked with an invisible, copy-surviving mechanism (text properties), not by prefixes, headings, or any syntax. Copying response text to another buffer preserves its identity as a response.
  • FR-TRACK-2 Four classes of buffer text exist: user prompt (default), response (LLM output), ignore (visible but never sent — e.g. reasoning fences, block delimiters), and tool records keyed by a call id (re-sent as structured tool messages).
  • FR-TRACK-3 Edits typed inside or immediately before a response extend the response (property stickiness); text typed after the end of a response, and at buffer end, is user text.
  • FR-TRACK-4 In non-chat buffers, tracking can be disabled entirely (gptel-track-response nil): all text is then user input. This knob has no effect in chat buffers.
  • FR-TRACK-5 Optional cosmetic prefixes before prompts and responses, configurable per major mode (gptel-prompt-prefix-alist, gptel-response-prefix-alist); they are inserted in chat buffers only, stripped before sending, and have no semantic role.
  • FR-TRACK-6 Navigation commands move point to the beginning/end of the response at or near point, with repeat counts.
  • FR-TRACK-7 An optional highlight minor mode (usable in any buffer) visually marks responses, ignored text, and tool blocks by any combination of: background face, fringe bitmap, or a margin bar (margin and fringe mutually exclusive).

3.3 Dedicated chat buffers (FR-CHAT)

  • FR-CHAT-1 A command (gptel) creates or switches to a named chat session buffer; prompts for name (default derived from the backend); prefix arg forces a new session; an active region becomes the initial prompt. If the backend’s API key cannot be resolved, prompt for it (password-style).
  • FR-CHAT-2 Chat buffers use a configurable major mode (gptel-default-mode: markdown if available, else text mode; org selectable) plus a minor mode (gptel-mode, keybinding C-c RET = send). The minor mode refuses to enable in unsupported major modes (must derive from org/markdown/text).
  • FR-CHAT-3 Any number of simultaneous sessions, each with independent buffer-local settings (backend, model, system prompt, tools, temperature, …).
  • FR-CHAT-4 A header-line UI (toggleable to mode-line + echo) shows: backend name; request status (Ready / Waiting / Typing / Calling tool / Run tools? / errors / Abort / Empty response — status is clickable and opens a request diagnostic); and right-aligned clickable indicators: token usage (toggles last-request vs session-cumulative), tool count (opens tool menu), media toggle (only for media-capable models), context summary (opens context inspector), system-prompt preview (opens directive menu), model name (opens main menu).
  • FR-CHAT-5 Token usage from provider responses is accumulated and displayed compactly (e.g. [12k↑, C4.1k↑ 890↓] with cached-token annotation), both per-request and per-session.
  • FR-CHAT-6 In markdown chat buffers, TAB on a code-fence line folds/unfolds the block (nested fences handled by parity).

3.4 Saving and restoring chats (FR-PERSIST)

  • FR-PERSIST-1 Saving a chat buffer to file persists the full conversation state: response/ignore/tool boundary positions, model, backend name, system prompt, tool names, preset name, temperature, max tokens, turn limit.
  • FR-PERSIST-2 In markdown/text files, persistence uses file-local variables; in Org files, Org properties at the top of the file (and optionally per heading). All persisted variables must be marked safe (no confirmation prompts on open).
  • FR-PERSIST-3 Opening a saved file and enabling the minor mode restores everything: text properties re-applied, backend/model/tools/preset resolved by name with graceful warnings for anything no longer defined (chat remains usable).
  • FR-PERSIST-4 When a preset is active, only settings that differ from the preset are written (minimal files; presets can evolve).
  • FR-PERSIST-5 A legacy bounds format (plain list of response ranges) must restore correctly.
  • FR-PERSIST-6 A pre-save hook lets users customize what is persisted.

3.5 Backends, models, keys (FR-BACKEND)

  • FR-BACKEND-1 Constructor functions register named backends for: OpenAI (and any OpenAI-compatible server), OpenAI Responses API, OpenAI via ChatGPT-subscription OAuth, Azure OpenAI, Anthropic, Google Gemini, Ollama, Kagi (FastGPT + Summarizer), AWS Bedrock (Converse), GitHub Copilot Chat, PrivateGPT, Perplexity, DeepSeek, xAI — with the OpenAI-compatible constructor additionally covering GPT4All, Groq, Mistral, OpenRouter, together.ai, Anyscale, Cerebras, Novita, Moonshot, llama.cpp, Open WebUI, etc.
  • FR-BACKEND-2 Each constructor accepts at minimum: display name, host, protocol, endpoint path, API key (string / variable / function), model list, streaming flag, extra headers (alist or function), extra request params, extra curl args.
  • FR-BACKEND-3 Models are declared with metadata: description, capabilities (media, tool-use, JSON output, URL input, no-system-message, caching, reasoning, audio, video…), supported MIME types, context window size, input/output costs, cutoff date, per-model request params. Capabilities gate features (e.g. media sending requires a media-capable model; system message suppressed for nosystem models).
  • FR-BACKEND-4 Model + backend selection UI presents all registered models as Backend:model with metadata annotations (description, caps, context window, costs, cutoff).
  • FR-BACKEND-5 API keys resolve through a chain: literal string / user function / Emacs auth-source lookup keyed by backend host with user “apikey”. Function-valued keys are called per request; trailing whitespace is trimmed.
  • FR-BACKEND-6 OAuth backends (GitHub Copilot; OpenAI/Codex subscription) implement device-code and/or PKCE authorization flows with token persistence, automatic refresh, and explicit login commands. Auth happens lazily and automatically on first request.
  • FR-BACKEND-7 The default backend can be configured declaratively (custom setter accepting a type+plist form) as well as programmatically.
  • FR-BACKEND-8 Per-request parameter layering: global extra params < backend params < model params (later wins).

3.6 Transport (FR-NET)

  • FR-NET-1 Requests use curl when available (configurable: t / nil / explicit path), falling back to Emacs’ built-in url-retrieve with no external dependency.
  • FR-NET-2 Streaming (incremental insertion of the response as it arrives) is supported only on the curl path and can be toggled globally/per-backend/per-model. Without curl, requests are still asynchronous but deliver the full response at once.
  • FR-NET-3 Proxy support (curl --proxy), user-configurable extra curl arguments, redirect following, compressed transfer, a stall timeout, and no limit on payload size (payload passed via stdin, not argv — also keeps keys out of the process list).
  • FR-NET-4 Multiple parallel curl processes must be demultiplexed reliably (per-request token protocol; see architecture).
  • FR-NET-5 Non-UTF-8 (binary) response streams must be supported for backends that need them (AWS Bedrock event stream).
  • FR-NET-6 Errors distinguish: connection-level failure (curl exit code), HTTP error with parseable provider error body, malformed JSON, unparseable response. No automatic retries.

3.7 Options menu and scoping (FR-MENU)

  • FR-MENU-1 A transient menu (gptel-menu, also C-u gptel-send) is the central control surface. It must show current state live and expose: model/backend selection; system prompt selection/editing; a one-shot “additional instruction” for the next request; context add/inspect/remove; tool selection; response length (max tokens); temperature; turn limit; context placement; reasoning handling; response tracking; media toggle; input redirection; output redirection; rewrite entry; response tweaks; dry-run and logging (behind an “expert commands” flag).
  • FR-MENU-2 Scope switch (= key, shared across all menus): every option set from a menu applies globally, buffer-locally, or oneshot (next request only, after which the previous value is restored — restore must survive the request machinery’s own let-bindings). The scope choice itself is persistent.
  • FR-MENU-3 Input redirection: prompt may be read from the minibuffer (with the option to include/exclude the active region, an “edit in buffer” escape hatch, history, and preset-cookie completion) or from the kill-ring (prefix arg selects which kill). Mutually exclusive with each other.
  • FR-MENU-4 Output redirection: response to the echo area, to the kill-ring (on error, partial output still copied), to an arbitrary buffer, or to a gptel session buffer (existing or newly created — the prompt text is inserted there, fenced as a code block in the target’s markup when source and target modes differ). “Respond in place” replaces the prompt with the response (region or trailing prompt text is killed; read-only text is left with a message; killed text is preserved as response history when possible). Streaming is disabled for echo-area and kill-ring destinations.
  • FR-MENU-5 The send button’s description is a live plain-English sentence describing exactly what will be sent, from where, with how many context sources, and where the response goes.
  • FR-MENU-6 Redirection options are per-invocation but can be persisted for the session (C-x C-s) and cycled through saved combinations.
  • FR-MENU-7 System prompt menu: pick from a user-configurable alist of named directives (string / function / string-list template forms), edit the current directive in a dedicated buffer (with read-only example header, C-c C-c/C-c C-k), unset it, or pick-and-edit from a crowdsourced prompt collection (fetched over the network only with consent; cached; refreshed after 14 days). Dynamically-generated (function) directives require confirmation before editing their current value.
  • FR-MENU-8 Tool menu: two-level category → tool selection with per-category toggle-all, selection state preserved for categories not currently displayed, confirm-tool-calls and include-results options, and a “continue pending tool calls” entry when a request is paused in the tool state.
  • FR-MENU-9 Menu visibility adapts to state: expert-only entries, mode-gated entries, capability-gated entries (e.g. system-prompt column hidden for nosystem models with an explanatory header), state-gated entries (context/rewrite/tool-continue only when applicable).
  • FR-MENU-10 Menus must work under evil-mode’s visual selections (region-gated entries appear correctly).

3.8 Presets (FR-PRESET)

  • FR-PRESET-1 gptel-make-preset defines a named bundle of settings: special keys :description, :parents (inheritance, applied first), :pre/:post thunks; :system (string / directive-symbol / function), :backend (name or object), :tools (names or objects, deduped); any other :foo sets variable gptel-foo (or gptel--foo), with unknown keys warning.
  • FR-PRESET-2 Values may be declarative modification specs: :append/:prepend (idempotent on strings), :eval, :function (old → new), :merge.
  • FR-PRESET-3 Presets are applied from the menu at any scope, via elisp, via a scoped gptel-with-preset macro (let-binding, no leakage), or per-request via an @preset-name cookie anywhere in the final user turn of the prompt — the cookie is removed from the sent text and only the last user turn is scanned. In chat buffers, valid cookies are fontified and completed at point.
  • FR-PRESET-4 A save-preset command snapshots current settings into a preset definition and copies the elisp form to the kill-ring. The menu displays the active preset and marks it (strike-through) if current state has drifted from it.
  • FR-PRESET-5 A built-in gptel-default preset resets all options to defaults.

3.9 Context system (FR-CTX)

  • FR-CTX-1 gptel-add (dwim): adds the active region as context (replacing overlapping previous context); toggles off the context at point; adds the whole buffer; in Dired adds marked files (directories recursively after confirmation); in ibuffer adds marked buffers; with negative prefix removes. gptel-add-file adds files/directories by path. A “yank to context” command adds the current kill (appending mode with prefix).
  • FR-CTX-2 Context is live, not snapshots: buffers/regions/files are re-read at each request time. Region context follows buffer edits (overlay semantics) and disappears when its text is deleted. Killed buffers and deleted files are silently dropped at collection time.
  • FR-CTX-3 Context entries support: whole buffers, buffer regions, files, file line-ranges and character-ranges, binary/media files (with MIME detection). Binary files require a media-capable model and a supported MIME; otherwise refused with a message. Images with misleading content encodings (ICC profiles) must still be detected as binary.
  • FR-CTX-4 In version-controlled projects, gitignored files are skipped by default (with a message naming the escape hatch, gptel-context-restrict-to-project-files); remote files are always allowed.
  • FR-CTX-5 Context is serialized per request into a structured string: each source gets a header (In buffer X: / In file Y:) and a fenced excerpt; sub-region excerpts get line-number markers and ellipses for discontinuities. The formatting function is replaceable and may be asynchronous.
  • FR-CTX-6 Placement is configurable (gptel-use-context): prepended to the system message (default), injected into the last user prompt (before its text), or disabled. For nosystem models, system placement automatically falls back to user placement. Media context files are attached to the first user message (media can’t ride in system messages).
  • FR-CTX-7 A context inspection buffer lists all context with previews (inline images for media), point-highlighting of the chunk under point, navigation (n/p), visiting the source at the corresponding position (RET), non-destructive deletion flagging (d) and batch confirm (C-c C-c) / quit (C-c C-k).
  • FR-CTX-8 The transient menu shows a live context summary (regions/buffers/files counts).

3.10 Media / multi-modal input (FR-MEDIA)

  • FR-MEDIA-1 With gptel-track-media enabled (global, buffer-local, or via the header-line/menu toggle) and a media-capable model, bracketed file/URL links in chat buffers (markdown: [](path), [desc](path), <url>; org: [[file:…]], [[attachment:…]], angle links) are parsed out of the prompt and sent as media parts (base64) or text-file parts. Plain unbracketed links are ignored.
  • FR-MEDIA-2 Every link in the prompt region is annotated in-buffer: a “SEND” badge when it will be sent; a warning badge with a tooltip explaining why not (unsupported link type, failed user predicate, unreadable, MIME unsupported by model). Links inside responses are never annotated or followed.
  • FR-MEDIA-3 A user predicate can restrict which links count (e.g. only standalone links on their own line); separate predicates for markdown and org.
  • FR-MEDIA-4 URL (non-downloaded) media parts are allowed only for models with the url capability.

3.11 Reasoning content (FR-REASON)

  • FR-REASON-1 Reasoning/thinking blocks in responses (delivered as separate API fields or inline <think> tags) are handled per gptel-include-reasoning: ignore (default — insert but mark as ignore so it is never re-sent), t (insert as normal response), nil (drop), or a buffer name (redirect there).
  • FR-REASON-2 When inserted, reasoning is delimited as an org #+begin_reasoning block or a markdown ```reasoning fence, auto-folded after insertion; delimiter lines are themselves marked ignore.
  • FR-REASON-3 Works identically for streaming (chunk-wise, with a reasoning-block state machine assuming reasoning precedes the answer) and non-streaming responses.

3.12 Tool use (FR-TOOL)

  • FR-TOOL-1 gptel-make-tool defines a tool: name (snake_case), description, elisp function, argument specs (name/type/description, optional flags, enums, arrays, nested objects), async flag (function receives a result-callback first), category label, per-tool confirm flag (boolean or predicate over the args), per-tool include-result policy. Tools are held in a category → name registry.
  • FR-TOOL-2 Selected tools (gptel-tools) are declared to the LLM with each request in the backend’s native schema format. gptel-use-tools: nil / t / force (require a tool call where the API supports it).
  • FR-TOOL-3 When the LLM requests tool calls, the client runs them locally and loops: results are sent back automatically and the request continues until a turn without tool calls. Parallel calls in one turn are supported; async and sync tools may mix; the continuation fires when all results are in.
  • FR-TOOL-4 Confirmation: global policy (always / never / per-tool “auto”), overridable per call by hooks. Pending calls are presented either as an in-buffer read-only block listing each call ((tool_name "arg" …), truncated) with a banner (Run: C-c C-c, Cancel: C-c C-k, Inspect: C-c C-i, mouse dispatch via multiple-choice), or via minibuffer multiple-choice (always used for read-only buffers).
  • FR-TOOL-5 An inspection buffer shows pending calls as editable plists; the user may edit arguments or delete calls entirely before approving; edits propagate into the outgoing message history.
  • FR-TOOL-6 Rejected tool calls leave the request paused and resumable (“continue tool calls” in the menu).
  • FR-TOOL-7 Sync tool errors become string results reported to the LLM (never break the request); a call to an unknown tool returns an error result listing available tools.
  • FR-TOOL-8 Tool call+result records are optionally inserted into the buffer as foldable blocks (org #+begin_tool, markdown ```tool) containing a machine-readable call plist + result, marked with the tool property so saved chats replay tool turns faithfully. Include policy: always / never / call (arguments only; the result is replaced by a cache notice on replay) / per-tool.
  • FR-TOOL-9 Pre/post tool-call hook points can block a call (with an error string to the LLM), stop the request, rewrite name/args (reflected in outgoing history), force/suppress confirmation, or replace the result.
  • FR-TOOL-10 MCP integration (separate opt-in library + external mcp.el): connect/disconnect commands register/unregister each MCP server’s tools under category mcp-<server>; connecting starts servers as needed, registers and activates their tools, reports partial failures; the tool menu gains “add”/“remove MCP tools” entries that preserve existing selections. Tool name collisions across servers are disambiguated by category.

3.13 Rewrite / refactor (FR-RW)

  • FR-RW-1 gptel-rewrite on an active region: prompts in the minibuffer for an instruction (default “Rewrite: …”, history, TAB shows the directive, C-c C-e full-buffer editing, M-RET opens the full options menu) and fires a rewrite request. Without region but with pending rewrites, opens the actions menu; otherwise errors.
  • FR-RW-2 The system directive defaults to a language-aware template built from the major mode (programmer variant for prog-modes: “generate ONLY code, no fences/explanations”; editor variant for text), overridable via a hook (first non-nil wins), the directive alist, or the menu. For nosystem models the directive folds into the user prompt.
  • FR-RW-3 The response is previewed in place over the original region (overlay display), streaming in live as the original text visibly morphs (grayed original shrinks as rewrite grows). The buffer is NOT modified. An overlay status line shows state (Waiting/Typing/tool states/Ready) and the model name.
  • FR-RW-4 On completion, the region pulses; the overlay becomes mouse/RET-actionable with eldoc + tooltip key hints. Actions: accept (replace original), reject/clear, iterate (re-rewrite using the pending output as input, previous instruction pre-filled), diff (with switch options), ediff (raw text, window config restored on quit), merge (conflict markers via git merge-file when git exists, manual markers otherwise; smerge-mode enabled). Batch variants act on all pending rewrites; navigation commands jump between rewrite regions.
  • FR-RW-5 gptel-rewrite-default-action runs one of these automatically on completion (or a custom function).
  • FR-RW-6 Multiple pending rewrites may coexist; aborting or erroring cleans up the overlay; a post-rewrite hook runs over the final text (in the staging buffer) before display.
  • FR-RW-7 The rewrite prompt is a 3-turn conversation (text-to-rewrite; canned assistant turn “What is the required change? I will generate only the final replacement.”; the instruction) to prime replacement-only output.

3.14 Org-mode extras (FR-ORG)

  • FR-ORG-1 Org prompts are sent as Org text (not converted), with cleanup: gptel’s own tool/reasoning block header lines stripped (avoid LLM mimicry), property drawers (configurable element list) removed, tool blocks unescaped.
  • FR-ORG-2 Topics: gptel-org-set-topic sets a GPTEL_TOPIC property on a heading; requests under it use only that subtree’s text — multiple independent conversations per file.
  • FR-ORG-3 Branching conversations (gptel-org-branching-context, needs Org ≥ 9.7, warns and degrades to linear otherwise): the conversation context is the outline lineage of point — each ancestor’s heading + direct body, sibling branches excluded; pre-heading top-of-file text included. Combines with topics/regions.
  • FR-ORG-4 Per-heading configuration: gptel-org-set-properties writes settings as Org properties (GPTEL_MODEL, GPTEL_BACKEND, GPTEL_SYSTEM with \n escaping, GPTEL_TEMPERATURE, GPTEL_MAX_TOKENS, GPTEL_NUM_MESSAGES_TO_SEND, GPTEL_TOOLS, GPTEL_PRESET); at send time inherited properties override buffer settings for that request only (preset property beats system property). Preset-aware minimal writes as in FR-PERSIST-4.
  • FR-ORG-5 Markdown→Org conversion of responses (gptel-org-convert-response, default on): LLM markdown (fences, inline code, headings, bold, italic, bullets) is converted to Org syntax on insertion. The streaming converter must produce byte-identical output regardless of chunk boundaries (holding back ambiguous trailing lexemes), must not transform emphasis inside code blocks, and must pass through literal Org src blocks the LLM already emitted.
  • FR-ORG-6 Org state persistence via GPTEL_BOUNDS property (see FR-PERSIST); writing must converge although inserting the property shifts the very offsets being written; long bounds lists must not be truncated.

3.15 Introspection, dry-run, logging (FR-INSPECT)

  • FR-INSPECT-1 Dry-run commands (menu, expert-gated) build the full request and show the payload in a buffer as pretty-printed Lisp or JSON. The buffer is editable; C-c C-c sends the edited payload (invalid edits produce a clear error); C-c C-w copies an equivalent shell curl invocation to the kill-ring. Dry-runs of async-transform requests must display once transforms finish.
  • FR-INSPECT-2 gptel-log-level: nil / info (request+response bodies) / debug (headers, curl config/command too) appended to a *gptel-log* buffer as timestamped JSON.
  • FR-INSPECT-3 A per-request diagnostic view (clickable status) shows the request’s state trail (e.g. INIT → WAIT → TYPE → DONE), INFO fields, and payload attributes — with message bodies scrubbed unless logging is on (privacy).
  • FR-INSPECT-4 Paused requests (dry-run, rejected tools) are resumable objects.

3.16 Response variants and regeneration (FR-VAR)

  • FR-VAR-1 Regenerate: delete the response at point (prefix/suffix swallowed in chat buffers) and re-send with current menu settings; the deleted text is retained as a variant.
  • FR-VAR-2 Variants at a position (from regeneration, rewrites, in-place replacements) can be cycled forward/back (point offset preserved, region pulses) and ediffed against the current text (variant choice via completion with prefix arg).
  • FR-VAR-3 A mark-response command selects the response at point.

3.17 Public extension API (FR-API)

  • FR-API-1 A documented programmatic entry point (gptel-request) accepts: prompt as string / list of alternating turns / structured turn list / nil (use buffer content); keys for callback, target buffer/position, arbitrary user context, streaming, system prompt override, dry-run, in-place flag, structured-output schema, prompt transform functions, and a pluggable request state machine. It returns a resumable request object and never blocks.
  • FR-API-2 The callback contract distinguishes: text chunks (streaming), full text, stream-done, nil+error info, abort, reasoning chunks/end, pending tool calls (with continuation closures), and tool results. Callback exceptions must never break the pipeline.
  • FR-API-3 Structured output: a :schema (elisp plist, JSON string, or shorthand DSL) forces a JSON response, encoded per backend (native JSON-schema modes where available; a forced synthetic tool elsewhere).
  • FR-API-4 Hook points (complete list): prompt transforms (sync/async, run in an isolated prompt staging buffer); post-request-dispatch; pre-response-insertion; per-stream-chunk; post-response (with response bounds; also fires on error/abort with degenerate bounds); pre/post tool call; save-state; buffer-refresh; context wrap; rewrite post-processing.
  • FR-API-5 Documented helper behaviors for hooks: auto-scroll on stream, move-to-next-prompt after response.

3.18 Provider wire protocols (FR-WIRE)

The client must implement, per provider, the exact request/response dialects — endpoints, auth headers, message shapes, streaming framing (SSE, JSONL, JSON-array, binary AWS event stream), tool declaration/call/result formats, media encodings, reasoning fields, prompt caching, token usage fields. The full protocol matrix is normative and specified in gptel-architecture.md §7–8. Notable non-obvious requirements:

  • FR-WIRE-1 Anthropic: max_tokens is mandatory; whitespace-only messages must be skipped; prompt caching via cache_control on system/tools/last message when enabled and model-capable.
  • FR-WIRE-2 Gemini: safety settings pinned to BLOCK_NONE; additionalProperties recursively stripped from schemas; no-arg tools need parameters: null (Anthropic conversely requires {}).
  • FR-WIRE-3 DeepSeek: strictly alternating roles — consecutive same-role messages must be merged.
  • FR-WIRE-4 OpenAI Responses API: kept stateless (store: false, full context each request).
  • FR-WIRE-5 Kagi: single-turn only, no streaming, no system message; summarizer takes the URL at point or region text.
  • FR-WIRE-6 Bedrock: sigv4 signing delegated to curl ≥ 8.9 (or bearer token); binary event-stream frames parsed without CRC validation.
  • FR-WIRE-7 Cross-provider conversation replay must tolerate foreign tool-call id formats.

4. Non-functional requirements

  • NFR-1 Emacs ≥ 27.1; Transient ≥ 0.7.8; optional markdown-mode; no other hard dependencies. Optional integrations: mcp.el, vterm, project.el (gitignore filtering), Org ≥ 9.7 (branching).
  • NFR-2 All network activity asynchronous; the UI thread is never blocked (including OAuth polling and tool loops).
  • NFR-3 The user’s point/window are never moved by default (P3); post-insertion hooks run with the buffer’s visible window selected so window-point is correct.
  • NFR-4 Request construction is isolated: prompt processing happens in a temp-buffer copy carrying a snapshot of all request options, so in-flight requests are immune to later user changes and transforms can’t damage user buffers.
  • NFR-5 Privacy: diagnostic views scrub message bodies unless logging is explicitly enabled; API keys never appear in argv; crowdsourced-prompt fetching requires consent.
  • NFR-6 Robustness: user callback errors demoted; tool errors stringified; malformed stream chunks retried on next chunk; buffer liveness checked before every insertion.
  • NFR-7 Performance: org element stripping defaults to the fast regex path (full org parses documented as “extremely slow”); binary-file detection reads ≤ 512 bytes; project file lists and link-type checks memoized; streaming insertion O(chunk).
  • NFR-8 All persisted file-local variables are safe-local-variable-marked.
  • NFR-9 Backwards compatibility: obsolete option aliases warn; legacy persistence formats restore.

5. Manual QA test cases

Conventions: each case lists Setup → Action → Expected. “Chat buffer” = gptel-mode buffer. Run the core send/stream suites against at least one streaming backend (curl) and once with curl disabled.

5.1 Basic sending

  • TC-001 Fresh text buffer, type a question, gptel-send → status Waiting → response inserted below point, separated by a blank line; cursor does not move.
  • TC-002 Select a region containing a question, send → only region content sent (verify via dry-run); response after region end.
  • TC-003 Point mid-word (“Explain recursi|on”), send → whole word included in prompt (dry-run).
  • TC-004 Type below a received response, send again → dry-run shows 2 user turns + 1 assistant turn in order.
  • TC-005 Edit the middle of a previous LLM response, then send → edited text appears in the assistant turn.
  • TC-006 Two buffers, send in both immediately → both responses arrive in the right buffers.
  • TC-007 gptel-abort mid-stream → insertion stops, status shows Abort, partial text remains, no stray processes (list-processes).
  • TC-008 Backend that returns an empty completion → status " Empty response", no separator/prefix inserted.
  • TC-009 Invalid API key → status shows HTTP error and provider message; nothing inserted; *Messages* has details.
  • TC-010 Network down → curl failure message with exit code; same for url-retrieve path.
  • TC-011 Kill the request buffer while a request is in flight → no error when the response arrives.
  • TC-012 Set turn limit to 1, long conversation, dry run → only the last user/assistant pair + final prompt sent.
  • TC-013 gptel-use-curl nil → sending works; streaming silently disabled even with gptel-stream t.
  • TC-014 Streaming on: response arrives incrementally; gptel-post-stream-hook (add a counter) fires per chunk; final buffer text identical to a non-streaming run of the same prompt (modulo sampling).
  • TC-015 With point kept at the insertion position during streaming, point rides the stream end; with point elsewhere, it never moves.
  • TC-016 Add gptel-auto-scroll to the stream hook → window scrolls when response passes bottom of window.
  • TC-017 Add gptel-end-of-response to post-response functions → cursor lands after response (next prompt prefix in chat buffers).
